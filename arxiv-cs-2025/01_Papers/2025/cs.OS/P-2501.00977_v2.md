# TL;DR（3行）
- 現代SSD（ZNS: Zoned Namespaces、FDP: Flexible Data Placement）のデータ配置ヒントを活用するため、アプリとファイルシステムの間にシム層「Valet」を挿入
- LD_PRELOAD（共有ライブラリを動的に差し替えるLinux機構）でlibcコールをインターセプトし、アフィニティ（書き込みストリーム分離）とライフタイム（削除タイミング）に基づくヒント生成
- F2FSに対して書き込みスループット2-4倍、テールレイテンシ最大6倍改善を達成（RocksDB、MongoDB、CacheLibで評価）

# Problem / Setting
- 入力/出力: アプリケーションのファイルI/Oコール → 配置ヒント付きI/O（または直接ゾーン配置）
- 目的: SSDのガベージコレクション削減、書き込み分離による性能・寿命改善
- 評価指標: スループット（ops/s）、レイテンシ（p50-p99.99）、書き込み増幅率
- 制約: ログ構造化アプリケーションが対象、mmap書き込みは非対応
- 比較対象: F2FS（Flash-Friendly File System: ZNS対応ファイルシステム）、ZenFS（RocksDB専用ZNSバックエンド）

# Key Contributions
- [シム層アーキテクチャ]: アプリ・FS・カーネル変更不要で配置最適化 → 3アプリ×2インターフェースで汎用性実証
- [アフィニティ+ライフタイム理論]: 従来の温度ベースヒントより細かいストリーム/グループ分離 → GC時のデータ移動0バイトを達成
- [valet-mapper実装]: ZNS向けホスト管理ストレージエンジン（バッファリング、GC、メタデータ管理） → ZenFS同等性能を汎用的に実現

# Method
- 前処理: LD_PRELOADでopen/close/read/write/fsyncをインターセプト、pathMap/fdMapでファイル追跡
- コアアルゴリズム:
  - ヒント生成: ストリーム（論理的書き込み単位、例:WAL（Write-Ahead Log）/SST（Sorted String Table））とライフタイムグループ（時間的サブセット）の2階層
  - ヒューリスティック: ファイルパス・拡張子からストリーム判定（例: `.log`→WAL、`.sst`→SST）
  - 自動学習: Mini-batch KMeansでopenフラグからストリームをクラスタリング
- 学習手順: オンラインでファイルopen特徴を収集、centroid数はvalet-mapperの推奨値を使用
- 推論手順:
  - ヒントベース（Multi-stream/FDP）: fcntl/fadviseでヒント注入
  - ホスト管理（ZNS）: valet-mapperがゾーン割り当て、エクステント管理、GC実行

# Experiments
- Dataset / Benchmark: db_bench（RocksDB）、wt-perf（WiredTiger/MongoDB）、cachebench（CacheLib）
- Metrics: スループット（K ops/s）、レイテンシ（μs、p50-p99.99）、書き込み増幅率、メモリ使用量
- Baselines: F2FS（+RocksDBヒント）、ZenFS（RocksDB専用）
- Setup: AMD EPYC 7452 64コア、128GB RAM、Western Digital Ultrastar DC ZN540 4TB×2、Ubuntu 22.04、Linux 6.5

# Results（主要数値）
- RocksDB fillrandom: Valet 350K ops/s vs F2FS 140K ops/s（2.5倍）、ZenFS 400K ops/s
- RocksDB p99.99レイテンシ: Valet ~20μs vs ZenFS ~555μs（27倍改善）
- WiredTiger read: Valet 26K ops/s vs F2FS 6K ops/s（4.3倍）
- WiredTiger update: Valet 22K ops/s vs F2FS 7K ops/s（3.1倍）
- CacheLib: Valetで8%スループット向上、p90以上のレイテンシ大幅改善
- GC: Valet データ移動0バイト vs F2FS 1059MiB、解放空間 48.2GiB vs 33.2GiB
- メモリ: valet-mapper 73MB vs F2FS 200MB

# Ablations / Analysis
- 効いたコンポーネント: ストリーム分離（WAL/SSTの物理的分離でデバイスバッファ競合解消）
- Valet-Learn（自動ヒント）: ヒューリスティックと同等性能、若干のテールスパイクあり
- マルチテナント: F2FSはp99.99で2倍劣化、Valetは小さな劣化のみ
- CPU時間: F2FSはsync 34%、Valetは27%以下（ZenFS同等）

# Limitations / Risks
- 再現性: ソースコード公開（https://github.com/shimplify/valet）
- 外的妥当性: ログ構造化アプリ限定、mmap使用アプリは部分対応
- 計算コスト: ユーザ空間オーバヘッド~2μs/syscall（LD_PRELOAD）
- 評価の穴: ZNS以外（FDP）は未実装、Golang/Javaアプリは非対応

# Relation to Prior Work
- ZenFS: RocksDB専用で高性能だがバージョンロックイン、開発停滞（2023年以降1コミット）
- F2FS: 汎用だがカーネル同期オーバヘッド大、3ヒントレベルでは不十分
- Multi-stream SSD/Open-channel SSD: いずれも非推奨化、限定的採用
- 本研究はアプリ/FS変更不要の汎用シム層として初めて複数アプリ×複数インターフェースを実証

# My Notes（解釈・疑問・使い道）
- ログ構造化システム（LSM-tree）向けの実用的なストレージ最適化手法
- シム層アプローチはハードウェアインターフェース変遷への耐性が高い
- FDP対応、より高度なML予測が今後の課題
